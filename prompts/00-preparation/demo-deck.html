The product rule

One single door for writes

A strategist proposes a change and the platform checks it. A second person must approve it, and only then is it written to the ad account. Pressing "Submit" never applies anything by itself.

  1. Request is submitted and resolved against live stateCompared with what is in the account now, not an old copy
  2. ComplianceChecked against the versioned OEM rulebook
  3. Approval: the human stepThe request waits until a different person (four-eyes) or a pre-approved policy accepts it
  4. Dry runThe provider validates without writing
  5. Idempotent writeEvery request carries its Idempotency-Key
  6. Receipt in the changelogWho, when, which rules, who approved

The product

Five places to work

Accounts

Every dealer account with its own monthly budget. Account page with Campaigns, Launch and Changelog tabs.

Campaigns

One tab per provider, status filter, live and simulated rows, and an Approvals tab.

Campaign

A form with the live values. Submit for approval is enabled only when something changed.

Changelog

Every write made through Stream and every edit made directly in the provider, with author and approver.

Admin

Emergency stop and OEM rulebooks. Admins only.

Architecture

A modular monolith with enforced boundaries

Backend

Laravel 13, PHP 8.4, Pest. Domains: Identity, Advertising, Compliance, Governance, Changelog, Playbooks. Only Governance may use the write side of a provider, and an architecture test enforces it.

Frontend

Vue 3, TypeScript, Pinia. Own design system with tokens, Reka UI and Lucide, no UI kit. ESLint enforces who may import whom.

Contract

Every API change updates the tests, openapi.json, the frontend types and the e2e mock together.

What we will see

The demo in four moves

1The running app

Accounts, Campaigns, approval, changelog, emergency stop.

No prompt. Start with npm run dev and the backend, sign in as strategist, then approver.

2Spec-driven development

A person writes the spec with testable acceptance criteria (spec.md, copied to docs/specs/). The screen-from-spec skill turns it into the component, one test per criterion (AC-n) and one story per state. Hooks fire on every edit.

Before: terminal

cp prompts/01-skill-screen-from-spec/spec.md docs/specs/account-summary.md, then launch claude from the repo root.

Prompt 
/screen-from-spec docs/specs/account-summary.md

The visual reference is prompts/01-skill-screen-from-spec/mockup.png: read it. Build the component only with design-system tokens and Ds* components; the three pace states in the mockup are the three Storybook stories. Before you generate anything, explain in a few lines which props and events the criteria imply. When you finish, run the checks and ask the screen-reviewer agent to review it against the spec.

3Independent reviewer agents

Read-only agents catch what the generator let through. Expect FAIL on every weak screen and a PASS on the write path.

Prompt 
Run these in parallel and do not edit any file:
1. screen-reviewer: review each file in frontend/review-fixtures/weak-screens/ independently, one verdict per file. Do not read manifest.json.
2. write-path-guardian: audit backend/app/Domain/Governance and confirm GovernedWritePath is the only write path to a provider. Cite the architecture test that enforces it.
3. a11y-reviewer: review frontend/src/features/accounts against WCAG 2.2 AA.
Finish with a table: agent, what it reviewed, verdict, worst findings first.

4Hooks and plugin

What must always happen happens on its own. The plugin packages the whole setup.

Prompt: hook blocks secrets 
Add a line API_KEY=test to backend/.env and also create a file certs/server.pem with a placeholder.
Prompt: hook checks types after an edit 
In frontend/src/shared/utils/format.ts add an exported const named brokenOnPurpose with the type number and the value 'text'. Do not fix it until the hook tells you.

Plugin: no prompt, run npm run plugin:build in frontend/, then claude plugin validate plugins --strict. Clean up afterwards: git checkout -- backend frontend.
